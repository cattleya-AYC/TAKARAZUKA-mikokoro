# 観劇会 申込フォーム(entry-form.html)README

小林タカラヅカ倶楽部の観劇会申込を受け付ける、参加者向けの単一HTMLページです。
Supabaseの`events`テーブルの状態に応じて、画面表示が自動で切り替わります。

---

## 1. 画面の状態(4パターン)

参加者がこのページを開くと、現在時刻とSupabaseのデータから、次の4状態のいずれかが自動表示されます。

| 状態 | 表示条件 | 内容 |
|---|---|---|
| ① 募集開始前(comingSoonCard) | 開催回はあるが`recruitment_start_date`(募集開始日時)がまだ先 | 「募集開始まで、しばらくお待ちください」+ 次回観劇会情報(第◯回・組・公演日時・募集開始日時)+ 締切済みで開催前の回の一覧(小さく表示) |
| ② 募集中(mainContent) | 現在時刻が募集開始日時〜締切の間 | 通常の申込フォーム(氏名・連絡先など入力) |
| ③ 締切後(thankYouCard) | 直近の開催回の締切を過ぎている | 「ご登録ありがとうございました」+ 結果連絡についての案内文 |
| ④ 開催回なし(closedCard) | Supabaseに該当データが1件もない | 「現在、募集中の回はありません」等の案内 |

切り替えロジックは`loadCurrentEvent()`関数が担当し、`events`テーブルを`application_deadline`・`recruitment_start_date`・`event_date`で判定しています。

## 2. 確認用プレビューモード

本番データを一切変更せずに、上記の画面を直接確認できる仕組みを用意しています。
URLの末尾に`?preview=◯◯`を付けてアクセスしてください。

```
https://takarazuka-mikokoro.vercel.app/entry-form.html?preview=thankyou   → 締切後の画面
https://takarazuka-mikokoro.vercel.app/entry-form.html?preview=coming    → 募集開始前の画面
https://takarazuka-mikokoro.vercel.app/entry-form.html?preview=closed    → 開催回なしの画面
```

※ Safari等でキャッシュが残っていて「Can't find variable」等のエラーが出た場合は、
　プライベートブラウズタブで開くか、URL末尾に`&v=2`のような適当な文字を足して再アクセスしてください。

## 3. 参照しているSupabaseのデータ(events テーブル)

| カラム名 | 用途 |
|---|---|
| `event_number` | 「第◯回」表示に使用 |
| `troupe` | 組(花・月・雪・星・宙)。テーマカラー自動切り替えにも使用 |
| `event_date` | 公演日(date型)。「◯月◯日(曜日)」表示に使用 |
| `show_time` | 公演時間の表示(◯時公演) |
| `recruitment_start_date` | 募集開始日時(timestamptz)。募集開始前/開始後の判定・表示に使用 |
| `application_deadline` | 申込締切日時(timestamptz)。募集中/締切後の判定に使用 |

`recruitment_start_date`が未設定(NULL)の場合、募集開始前の判定がうまく機能せず、
「締切前なら常に申込めてしまう」不具合が起きるため、**開催回登録時は必ず入力してください**。
(`admin-new-event.html`から新規登録すれば自動計算されます)

## 4. 参加者(participants)の同一人物判定について

フォーム送信時、Supabaseの`participants`テーブルに「同じ人」を正しく1人として記録するため、
**お名前(全角・半角スペースを取り除いたもの)で既存の参加者を検索**し、一致すればその参加者IDを使い、
一致しなければ新規に参加者を作成します。

- 以前はメールアドレスで同一人物を判定していましたが、入力ミス・毎回違うアドレスの使用・
  家族間でのメールアドレス共有などにより、「同じ人が別人として複数登録される」
  「逆に別人が同一人物として扱われる」という2種類の問題が起きていたため、
  **名前ベースの判定に変更しました**(2026年8月〜)。
- 名前が一致して既存の参加者と判定された場合、メールアドレス・電話番号は
  その回の入力内容で毎回上書き更新されます。
- **注意**:同姓同名の別人がいる場合、誤って同一人物として扱われる可能性があります。
  同姓同名の参加者がいることがわかっている場合は、`admin-list.html`側で
  申込み後に参加者データを手動で分離するなどの対応が必要です。
- 過去にメールアドレス判定で分かれてしまっていた参加者データは、
  `merge-duplicate-participants.sql`で名前ごとに1人へ統合済みです
  (この移行は完了しており、再実行しても影響はありません)。

### 4-1. 名前の正規化がすり抜けるケース(2026年8月・実例あり)

上記の名前正規化は「全角・半角スペースを取り除く」処理ですが、**スペースの有無そのものが
表記ゆれの原因になり、正規化後の比較タイミングによっては別人として2重登録されることがある**
ことが判明しています。

- 実例:「小岡　潤子」(全角スペースあり)と「小岡潤子」(スペースなし)が、`participants`テーブルに
  別々の2レコードとして存在していた(2026年8月29日、第21回星組公演)。
  片方にはペナルティ履歴(`penalty_points`・`penalty_notes`)が付いており、もう片方には何もなかった。
- この状態だと、一覧の人数は合っていても、ペナルティや過去の参加履歴が
  正しいレコードに集約されず、見た目上「参加履歴がない/ポイントがおかしい」ように見える。
- **対処**:見つかった場合は手動でSQLを実行し、履歴のある方のIDへ`registrations`・
  `change_logs`の`participant_id`を付け替えたうえで、履歴のない方を削除して1件に統合する。
- **教訓**:名前正規化のロジックは、今後も表記ゆれのパターン(全角/半角スペース、スペース自体の
  有無、旧字体、ミドルネーム的な表記など)が新たに見つかるたびにすり抜ける可能性がある。
  定期的に次のようなクエリで重複がないか確認するのが望ましい。

  ```sql
  select regexp_replace(name, '\s', '', 'g') as normalized_name, count(*), array_agg(id)
  from participants
  group by normalized_name
  having count(*) > 1;
  ```

### 4-2. `admin-list.html`側でこの参加者IDがどう使われるか(重要な注意点・2026年8月に方針修正)

`admin-list.html`の申込者一覧は、申込データ(registrations)に`participants`テーブルを
結合(embed)して氏名等を表示しています。この結合の書き方(`participants(...)` か
`participants!left(...)`か)によって、**参加者側のレコードが解決できない申込みが
「行ごと画面から消える」不具合が過去に発生しました**
(第21回星組公演で「61回生 小岡 潤子」の1件が22名中21名表示になっていた事例)。

- **2026年8月時点の結論**:このプロジェクトの実データでは、`admin-list.html`が
  `participants!left(id, name, ...)`(明示的な外部結合ヒント)を使っていたときに1件だけ
  表示から消え、正常に全件表示できていた`admin-list-view.html`は`participants(id, name, ...)`
  (結合ヒントなし)を使っていた。**`!left`を外し、結合ヒントなしの書き方に揃えたことで
  解消した**(この時点では`registrations`→`participants`間の外部キーが1本しかなく、
  ヒントなしのデフォルトが左外部結合として振る舞っていたと考えられる)。
- **重要**:「`!left`を付ければ安全」「`!left`を外せば安全」という単純な話ではない。
  PostgRESTの埋め込み結合は、テーブル間の外部キー構成(本数・NULL許可有無)によって
  ヒントなし時のデフォルト挙動が変わりうる。**新しく結合コードを書く・コピーする際は、
  必ず「Supabase上の申込者数」と「画面に実際に表示された行数」が一致するかを都度
  目視確認すること**。件数が合わない場合は、まず結合ヒント(`!left`の有無)の違いを疑う。
- 件数が合わないバグの調査手順の定石:①Supabaseから取得できた件数(fetch件数)を
  console.log等で確認 → ②filter/slice/重複排除ロジックを確認 → ③埋め込みJOINの
  結合方式(ヒントの有無・inner/left)を、**現在正常動作している別ページのクエリと
  1行ずつ突き合わせて**確認、の順で切り分けると早い。

## 6. 運用上の注意

- 開催回のデータは**必ず`admin-new-event.html`から登録**し、募集開始日・締切日が正しく自動計算されるようにしてください。手動でSQLを直接いじる場合は、`recruitment_start_date`と`application_deadline`の両方を入れ忘れないよう注意してください。
- 締切日時は21:00固定、募集開始日時は朝9:00固定というルールで運用しています。
- 複数開催回を同時に募集する運用は想定していません(常に1つの開催回のみが「募集中」になる前提です)。
- データベースの構造変更(マイグレーション)を伴う修正は、**必ずSupabase側のSQL実行を先に行ってから**、フロントエンド(Vercel)のデプロイを行うこと。逆の順序で進めると、フロントエンドが未反映のテーブル/ビューを参照してエラーになる。
  - **具体的な失敗の見え方(2026年8月に実際に発生)**:順序を間違えても画面が真っ白になったりクラッシュしたりはしない。Supabase側がエラーを返し、コード側のエラーガード(`if(!error && data)`等)によって静かに握りつぶされ、**該当箇所の数字がすべて「-」表示になるだけ**なので気づきにくい。集計・ポイント表示が急に「-」だらけになったら、まずSQL実行順を疑うこと。
- **Supabaseのプロジェクト取り違えに注意**:このクラブでは観劇会システム用(「小林タカラヅカ倶楽部」)以外にも、お店の業務用(レジ・在庫管理、テーブル名は`sales`・`orders`・`cake_stock`等)の別プロジェクトを併用している。SQL Editorを開く前に、**必ず左上のプロジェクト名を確認**すること。誤って別プロジェクトに`registrations`/`participants`向けのSQLを実行しても、該当テーブルが存在しないためエラーになり実害はないが、心臓に悪いので事前確認を習慣にする。

## 7. 観劇会申込(registrations)と食事申込(meal_orders)のデータ整合性について

食事申込システム(`entry-form.html`とは別の`kengaku_`系テーブル/`meal-*.html`)は、
観劇会本体の申込(`registrations`)とは**別テーブル・別フローで管理**しており、
DB上の外部キー制約や自動連動の仕組みはありません。そのため、次のようなズレが起こり得ます。

- 観劇会を**欠席・キャンセルした人**の食事申込データが`meal_orders`に残ったままになると、
  食事の集計(参加人数・メニュー数・ドリンク数)だけ実際より多くカウントされる。
  (実例:第◯回で観劇欠席の参加者の食事データが残っており、参加人数「18名」のはずが
  集計上「19名」になっていた)
- `lunch-summary.html`の参加人数は`registrations`(観劇「ご参加」)ベースで計算している一方、
  メニュー別・ドリンク別集計は`meal_orders`から直接集計しているため、**片方だけズレる**
  ことがある。両者の数字が食い違ったら、まずこの2系統の集計元の違いを疑うこと。
- **教訓**:観劇会を欠席・キャンセルにする運用が発生した場合、`registrations`側の変更だけでなく
  `meal_orders`側の該当データも手動で確認・削除する必要がある。将来的には、欠席確定時に
  対応する`meal_orders`を自動的に無効化/削除する仕組み、または `lunch-summary.html`側で
  「観劇未参加なのに食事データがある人」を自動検出して警告表示する仕組み(`invalidOrders`)
  を強化することが望ましい。

## 8. ポイント制度(直近参加実績)について

`admin-list.html`・`admin-list-view.html`の一覧に表示される数字は、
`v_recent_participation`というSupabaseのビュー(直近7回・`status <> 'キャンセル'`の申込件数)から
`recent_count`を取得し、`recent_count − penalty_points(ペナルティ)`で計算した値です。

- 2026年8月に「申込+1点、食事申込+1点」というルールへの変更を試みたが、実運用への影響を
  検証しきれず、**現時点では元の「直近参加数−ペナルティ」の式に戻している**。
- 変更を再度試す場合は、`v_recent_participation`に`recent_meal_count`列を追加するSQLを
  **先に**実行してからフロントエンドを更新すること(順序を間違えると6章の「-」表示問題が起きる)。
- ペナルティは「変更・キャンセルを記録」モーダルの「ペナルティも記録する」チェック(初期値ON)で
  加算される。食事のみのキャンセルであっても、そのキャンセル自体を禁止事項として運用している
  場合はチェックを外さずそのまま記録してよい。

## 9. 印刷機能について(2026年8月時点の運用方針)

`admin-list.html`の申込者一覧をブラウザから直接PDF印刷する機能は、**iOS Safariの印刷エンジンが
表の途中で正しく改ページできず、最後の1行が印刷されずに消えることがある**という問題が解消できず、
運用から外している。

- CSS(`page-break-inside:avoid`等)による対策、`beforeprint`イベントを使い実際の行の高さを
  JavaScriptで測定して手動で改ページ位置を指定する対策、いずれを行っても改善しなかった。
- そのため、**`admin-list.html`からは印刷ボタンを削除済み**。印刷が必要な場合は、
  別途用意しているスタッフ用アプリから行う運用に変更した。
- 今後もし`admin-list.html`側での印刷を再検討する場合は、ブラウザの自動改ページに頼らず、
  1ページ分の行数を固定して`<table>`ごとページを分割する等、より根本的な設計変更が必要になる
  可能性が高い。

## 11. メールアドレス入力欄の不具合(2026年9月・修正済み)

- entry-form.htmlのメールアドレス入力欄に`list="emailList"`+`<datalist>`が設定されており、`loadKnownEmails()`関数が`participants`テーブルの全メールアドレスを取得して候補表示していた。
- 結果、参加者が入力欄をタップすると**他の参加者のメールアドレスが候補一覧として見える状態**になっていた(2026年9月、複数会員から報告)。
- **原因**:入力補助のつもりで実装した機能が、実質的に個人情報を画面上に一覧表示する形になっていた。
- **対処**:`list`/`datalist`属性および`loadKnownEmails()`関数を削除。入力補助機能自体を廃止した。
- **教訓**:今後、入力補助・オートコンプリート的な機能を追加する際は、**他人の個人情報(メール・電話番号等)を候補やリストとして画面に出す実装になっていないか**を必ず確認すること。似たような機能(電話番号の入力補助など)を作る場合も同様の注意が必要。
